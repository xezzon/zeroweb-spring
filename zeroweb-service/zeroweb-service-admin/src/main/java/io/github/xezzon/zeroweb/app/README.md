# 服务管理

## 应用自省设计文档

### 需求背景

在微服务架构中，通常存在大量的服务实例。传统的服务管理方式需要在中心化的配置中心或者管理界面中维护所有服务的信息，例如服务的访问路径、提供的菜单等等。这种方式存在以下问题:

* **配置繁琐:** 每次新增、修改或者删除服务，都需要修改中心化的配置，容易出错。
* **可扩展性差:** 当服务数量增加时，中心化配置的维护成本会变得非常高。
* **实时性差:** 服务信息的变更可能无法及时同步到配置中心，导致管理界面显示的信息不准确。

为了解决这些问题，我们引入了应用自省的设计。

### 设计目标

* **简化配置:** 只需要配置应用的基础访问路径，即可通过自省的方式获取应用信息、菜单等内容。
* **提高可扩展性:** 服务信息的维护由各个服务自身负责，中心化的配置中心只需要维护少量信息。
* **保证实时性:** 通过自省的方式获取服务信息，可以保证管理界面显示的信息与服务的实际状态一致。

### 实现方式

每个服务都提供一个标准的自省访问点，例如 `/metadata`
。该访问点返回服务的基础信息、提供的菜单等等。管理界面只需要知道服务的基础访问路径，即可通过访问该自省访问点获取服务信息。

### 前后端自省结构一致性

为了简化前端的开发工作，我们要求前后端自省结构保持一致性。例如，如果后端服务的自省访问点返回的菜单数据结构如下:

```json
[
  {
    "name": "用户管理",
    "path": "/user"
  },
  {
    "name": "角色管理",
    "path": "/role"
  }
]
```

那么前端也应该使用相同的数据结构来渲染菜单。

### 所有服务自省访问点相同

为了简化管理界面的开发工作，我们要求所有服务的自省访问点相同。例如，所有服务都提供 `/metadata` 访问点。

### 总结

应用自省的设计可以简化配置、提高可扩展性、保证实时性，从而提高微服务架构的可维护性和可管理性。保持前后端自省结构一致性和所有服务自省访问点相同可以简化前后端的开发工作。
